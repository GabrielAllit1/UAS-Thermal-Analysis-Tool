# UAS Thermal Analysis — Agent Guide

This file records durable repository architecture and quantitative invariants. It is not a session log.

## Production hierarchy

New product development targets `src/uas_thermal/`. Root-level legacy modules remain compatibility references until measured parity permits explicit retirement.

Canonical subsystem ownership:

- `application/`: projects, datasets, desktop workspace, processing state, orchestration.
- `thermal/`: calibration, radiometric quality, contextual detection, statistics, validation.
- `sensors/`: vendor/source decoding into `ThermalFrame`.
- `geospatial/`: display rasters, transforms, overlays, KML/world-file handling.
- `inspections/`: canonical findings, profiles, lifecycle, deduplication, comparison.
- `reporting/`: annotations, finding plates, reports, machine-readable exports, packages.
- `platform/`: configuration, logging, packaging, licensing boundary.

## Canonical authorities

### Quantitative source authority

Only validated radiometric sources decode to `sensors.base.ThermalFrame` and may enter temperature analysis.

`geospatial.display.DisplayRaster` is presentation/GIS data only. It must never acquire a temperature matrix or be passed into quantitative anomaly detection.

### Inspection execution authority

`application.orchestrator.AutonomousInspectionOrchestrator` is the canonical dataset-to-findings execution path. GUI, CLI, batch, and future APIs should reuse it rather than duplicate analysis stages.

### Finding authority

`inspections.models.Finding` is the canonical finding model. UI rows, map features, annotations, CSV/JSON/KML/GeoJSON, and PDF report entries are projections of this model. Do not create report-only or UI-only finding truth.

### Profile authority

`inspections.profiles.InspectionProfile` supplies versioned domain interpretation while the quantitative detector remains vendor- and domain-neutral.

## Required quantitative boundaries

Preserve these distinctions:

```text
display raster != radiometric source
high temperature != defect
candidate != finding
severity != confidence
confidence != certification
GPS coordinate != physical-defect identity
duplicate cluster != proven same asset without evidence
automated report != thermographer certification
unit test != field validation
successful execution != verified quantitative correctness
```

Do not fabricate unavailable temperatures, coordinates, confidence probabilities, asset identity, calibration evidence, or certification.

## Detection design

The principal detector is `thermal.anomaly_detection.analyze_temperature`.

It uses local contextual references, local ΔT, multi-scale support, robust scene evidence, morphology, and explicit suppression. A global scene median is permitted as a documented fallback, not the sole principal detection authority.

Suppression reasons should remain explicit and testable.

## Radiometric quality

Run `thermal.quality.evaluate_radiometric_quality` before quantitative detection. Rejected sources must not silently enter the thermal engine. Per-source failure should be isolated where practical so one bad image does not terminate a valid large inspection.

## Geospatial authority

CRS assumptions must remain explicit. `geospatial.transforms.crs_warning` prevents suspicious/local CRS text from silently becoming WGS84 authority. Do not hard-code project-specific State Plane systems globally.

A display orthomosaic may present already-geolocated findings but does not become the thermal measurement authority.

## Reporting and provenance

Required provenance direction:

```text
report/map/table/annotation/export
              ↓
       canonical Finding
              ↓
 quantitative characterization
              ↓
       ThermalFrame region
              ↓
 original radiometric source
```

Allowed report language includes:

> Automated thermal analysis and anomaly classification generated by UAS Thermal Analysis.

Do not claim thermographer certification unless a qualified person actually reviewed and signed the work.

## Large-data discipline

Do not decode every full-resolution source into memory at once. Preserve bounded display reads and existing full-frame safety limits. Prefer lazy decoding, bounded concurrency, tiling/overviews, and incremental output for future large-dataset work.

## Vendor integrations

Vendor-specific SDK code terminates in `sensors/`. Downstream thermal, inspection, map, and report code must stay vendor-neutral.

Do not commit vendor SDK DLLs or binaries. Do not infer radiometry from a filename or thermal-looking palette.

## Commercial licensing

The current licensing module is a boundary, not the final paid subscription implementation. Do not embed symmetric signing secrets in the paid desktop client. Automated subscription entitlement remains a later production tranche after application/analysis/Windows distribution convergence.

## Validation commands

Run before promotion:

```powershell
python -m compileall src
pytest -p no:cacheprovider
ruff check src tests
python -m uas_thermal validate-synthetic
```

For Windows product validation also launch:

```powershell
python -m uas_thermal desktop
```

When a genuine supported radiometric source is available, run the vendor/source diagnostic and the canonical `inspect` command before claiming field/runtime parity.

## Source-control discipline

Preserve user data and local vendor runtimes. Do not reset, clean, delete, or overwrite unrelated local work. Customer inspection datasets, generated reports, secrets, and vendor binaries remain outside source control.
